## 4. R03 · P2 · CASE_MAP 的表头、分类计数和删除依据需补齐

位置：`CASE_MAP.tsv:3`～`:5`、`:69`。

1. **表头不是五列。** 第一个非注释行开头多一个制表符，形成六列表头，正文为五列；普通 TSV 读取器也会把前置说明当作表头。请采用明确的五列表头 `scope / group_or_case / action / carrier / basis`，或明确跳过注释的读取约定，并去掉空字段。
2. **总删除数 321 正确，分组有误。** 独立按旧清单和删除计划勾稽：平层历史非活跃夹具 **226** + 原活跃夹具 **93** + 独立故障控制文件 **2** = **321**。当前“清单内未保留项 95 个”把后两类混合；末尾 witness_faults 行又单独列出 2 个，容易重复统计。应明确互斥分组；当前 63 个 UI 文件来自 61 个主项 fixture + 2 个见证，消费者另计一条清单行。
3. **93 个现役删除项不能只按错误码分组判等价。** “同类错误码/同类借用冲突”不能独立证明契约相同。例如 Root 输出上限与 Node 输入上限都可能报 E0277，但检查的调用边界不同。请按契约类别给明确成员清单/现有 ui_prune_plan 引用，指向保留下来的新 fixture、Rust 测试或参数化场景及其关键判据；也可明确说明原契约已失效。不要求恢复全部 93 个夹具，也不要求为每个重复断言写账本。

整理后的 CASE_MAP 需要同时容纳实际 Rust 精简结果；只在 target 中存在的未落地计划应标记为计划或不纳入已完成交付。

计数、列宽与新旧判定字段对照见 `target/test-cleanup-review-R1/TABLE_AUDIT.json`。
